Holding a goal until it is reached

Progress on letting the manager keep a goal for a variable number of steps. Updated __DATE__. The status table at the end shows what is done, running and open.

1 · The question

Why did variable goal holds score lower?

In Director the manager picks a new goal every 8 steps. We changed this: the manager keeps a goal until the worker has reached it, or until a cap (8, 16 or 32 steps) runs out. Reached means the state matches the goal well enough:

On the pin pads this scored clearly below plain Director with our settings (called V), at every cap. Three control runs on pin pad four, all with cap 8, looked for the cause:

So everything works as long as every hold has exactly 8 steps. The drop appears only when holds end at irregular times.

2 · What was found

A wrong bootstrap for the last hold of each imagined rollout

The manager learns from imagined rollouts of 16 or 32 steps. The return of a decision is the reward collected during its hold plus the value of the state where the hold ends:

The last hold of a rollout is usually cut off by the end of the rollout. Its return must then use the value of the final imagined state. The code used the value of the state where that hold started:

The wrong version teaches the value function a loop:

In words: "the reward of these 6 steps comes again every 6 steps, forever". On a pin pad the reward is one large payment at the end of a sequence, so states just before a payment get a value many times too high. With a smooth reward (cartpole, cheetah) the loop is close to the truth, which is why those tasks looked fine.

How it was found: a new test file runs the real agent and recomputes every stage of the variable-length path by hand (24 checks: switch rule in the environment, imagination, manager and worker training tensors, replay). 23 agreed; the bootstrap state did not. A last test compares the return itself with a hand-written one. The fix is small and switched on by default (goal_duration_trailing_boot). Every earlier variable-length run, including the old manager-chosen durations, had this error.

Three findings. (1) Ending a hold when the goal is reached is what helps: a control with fixed 4-step holds and no reached test never scored in 3M steps, so shorter holds alone are worse than 8. (2) The worker "done" rule works and is not gamed: it ends holds after 3 to 6 steps and learns pin pad five as fast as the best rule. (3) Letting the manager pick any length from 1 to 32 does not work: nothing pushes it to short holds before the first reward, so it stays near 15 steps. A 1 to 8 version is queued.

Pin pad six is still unsolved by every rule (0 in 5 runs), with or without surprise. It is an exploration problem; runs with the earlier transition-count bonus on top of reach-or-8 are queued. Cheetah with reach-or-8 is at about 500 at 1.3M, in line with V.

One more inconsistency found and being tested. When the manager's value is trained on recorded experience, the code re-decided where goals would switch using today's manager on old data. Old data was following other goals, so "reached" almost never fires there and holds run to the cap: 22 to 29 steps in training against 10 to 11 in reality at cap 32. A new option stores the real switch points and trains on those. Cap 32 runs with it are queued.

Worker "done" is computed from the worker's own value estimate: stop when the expected future match is no better than keeping the current match, , and the match is at least half the ceiling. The worker cannot gain by stopping early, because stopping only pays what it already has.

5 · Next designs

What will be tested after the fix is confirmed

  1. Other caps. 16, and 48 with a longer imagined rollout (rollouts are 16 steps by default and 32 for cap 32, so a full 32-step hold just fits).
  2. Threshold. Sweep the reached fraction around 0.8 (lower fires earlier and more often, higher waits for a closer match). Cap 32 throughout.
  3. Reached by distance. Use the squared error between goal and state, against a running reference, in place of the cosine match.
  4. Worker says "done". The risk: many short goals can pay the worker more than one long goal, so it would always say done. Two guards to try: a done only counts when the match test also passes; and each switch costs the manager a small price, so short holds must earn it back.
  5. Manager picks the length. The old duration head, rerun with the fix. All earlier results of this arm carried the bootstrap error.
  6. Surprise. Reward the manager for goals that lead to more surprise than usual, , in place of the count-based exploration term.
